# Code Review: Bold.co donation method

**Scope:** `src/lib/bold.ts`, `src/pages/api/bold-firma.ts`, `src/pages/api/bold-webhook.ts`, `src/pages/api/bold-confirmar.ts`, `src/pages/api/donante.ts`, `src/components/Registration.astro`, `src/templates/GraciasTemplate.astro`, `src/pages/admin/donadores.astro`, `src/i18n/locales/*.json`, `migrations/0002_add_payment_provider.sql`. (`worker-configuration.d.ts` excluded — generated by `wrangler types`.)

**Overall:** ✅ Passes. No critical/high issues. Security is sound: the secret key never reaches the client (verified via curl — `bold-firma` returns only the computed signature + identity key), the webhook re-queries Bold instead of trusting the payload, and confirmations are idempotent (`WHERE status='pending'` + unique partial index). Findings below are low/medium polish items.

---

severity: medium
file: src/pages/admin/donadores.astro
line: 40-42
issue: "Total Recaudado" stat sums amounts across mixed currencies (COP + USD)
detail: `stats.totalAmount` reduces `donor.amount` over all completed rows regardless of currency, then renders it as COP via `formatCurrency(stats.totalAmount)`. After this change a completed PayPal row (USD, e.g. 25) and a Bold row (COP, e.g. 100000) are added into the same figure, producing a meaningless "$100.025 COP". This was already imperfect pre-change but is now actively mixing two real currencies.
suggestion: For v1 (per the agreed "counter by donor count" decision) either (a) replace the "Total Recaudado" card with a donor count, or (b) split the total into two cards (COP total and USD total) by filtering `donor.currency`. Tracked as a plan follow-up; acceptable to defer but should not be presented as an accurate fundraising total.

severity: low
file: src/components/Registration.astro
line: ~648-658 (loadBoldSDK)
issue: `boldSdkLoaded` flag is set before the script finishes loading, so a concurrent caller can resolve before `window.BoldCheckout` exists
detail: `activateMethod('bold')` calls `loadBoldSDK()` (sets flag, starts loading). If the user clicks "Bold" and immediately clicks the pay button, the second `loadBoldSDK()` sees the flag and resolves instantly even though the SDK may still be downloading. The downstream guard `if (!window.BoldCheckout) { showToast(error); return; }` prevents a crash, but the user may have to click twice.
suggestion: Cache the load promise instead of a boolean: `let boldSdkPromise: Promise<void> | null; const loadBoldSDK = () => (boldSdkPromise ??= new Promise(...))`. Then every caller awaits the same real completion. Low impact in practice (SDK is usually loaded by the time the user submits).

severity: low
file: src/lib/bold.ts
line: 70-95 (fetchBoldVoucher)
issue: Defensive parsing relies on `Record<string, any>` and guesses field names for the voucher payload
detail: The exact Bold `payment-voucher` response shape is not yet confirmed, so the code reads `status ?? payment_status ?? transaction_status` and `transaction_id ?? payment_id ?? id`. The `any` usage is intentional here, but if Bold's real field names differ from all guesses, a successful payment could be read as `pending` (fails safe — never falsely completes).
suggestion: Once a real voucher response is captured from the Bold panel/sandbox, narrow the type to the actual fields and drop the unused fallbacks. The fail-safe direction (defaults to pending) is the correct bias for now.

severity: low
file: src/pages/api/bold-webhook.ts
line: 11-20 (signature verification deferred)
issue: Webhook does not yet cryptographically verify Bold's signature
detail: Documented with a `TODO(bold-webhook-signature)` comment. Mitigated by design: the handler treats the payload only as a trigger and re-queries Bold server-side for the authoritative status, so a forged webhook cannot complete a donation without a real Bold transaction. Acceptable for v1.
suggestion: When the signature header/scheme is confirmed from the Bold panel, add HMAC verification of the raw body and return 401 on mismatch (before re-querying).

severity: low
file: src/pages/api/bold-firma.ts
line: 30-33
issue: Non-JSON request body yields a 500 instead of 400
detail: `JSON.parse(raw)` throws on malformed bodies and is caught by the outer `catch` that returns 500. A malformed client request is a 4xx, not a server error.
suggestion: Wrap the `JSON.parse` in its own try/catch and return 400 "Invalid JSON". Minor; does not affect the happy path.

## Verified (no issues)

- **Secret handling:** `BOLD_SECRET_KEY` is used only in `bold-firma` to compute the signature and is never included in any response (confirmed by curl: response contains `apiKey` = identity key only).
- **Idempotency:** `confirmBoldOrder` updates only rows with `status='pending'`; combined with the unique partial index on `bold_order_id`, duplicate webhook + `/gracias` confirmations cannot double-count. Verified: a repeated webhook returned `changed:false`.
- **PayPal regression fix:** `donante.ts` now persists `transaction_id`/`provider_status`; existing response shape `{success, id}` unchanged (Registration.astro still reads `data.id`).
- **Migration safety:** one column per `ALTER TABLE` (SQLite constraint); defaults (`'paypal'`/`'USD'`) keep existing rows consistent; partial unique index allows multiple NULL `bold_order_id` (PayPal rows).
- **Signature correctness:** SHA-256 of `{orderId}{amount}{currency}{secretKey}` matches Bold's documented example hash.
- **Routes:** new endpoints are distinct static paths (`/api/bold-firma`, `/api/bold-webhook`, `/api/bold-confirmar`); no parameterized-route shadowing.
- **i18n:** new keys added to all three locales (es/en/fr); JSON valid; build passes with no missing-key type errors.
